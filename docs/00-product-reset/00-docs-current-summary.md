# Docs 当前状态总览

## 1. 整体情况

当前 `docs/` 已覆盖项目总览、产品设计、用户角色、功能架构、技术架构、数据模型、API、UI、研发计划、验收、Issue 拆分、支付专项、论文工作台、OnlyOffice、学术数据、订单重构等主题。它记录了从“论文生产与交付平台”到“论文文档工作台 + 支付生产化 + 学术数据底座”的多轮开发演进。

整体判断：文档信息量充足，但组织方式已经从稳定的“产品决策文档”逐步变成“开发过程堆积文档”。同一编号、多轮计划、专项补丁和实现记录混杂在根目录，已经影响后续产品方向纠偏与市场 MVP 判断。

## 2. 当前 docs 最大的问题

1. **编号冲突明显**：存在两个 `08`、两个 `12`、两个 `13`、两个 `14`、两个 `15`，且部分文件名含空格或拼写错误，降低检索和引用可靠性。
2. **主题重复明显**：项目定位、MVP、用户流程、功能架构在 `00/01/02/03` 之间反复出现；开发计划在 `08-development-plan.md`、`08-development-roadmap.md`、`11-development-execution-plan.md`、`14-next-development-plan.md` 中交叉。
3. **层级混杂**：根目录同时放置产品蓝图、开发任务、支付审计、OnlyOffice 部署、学术数据导入、订单重构调研，缺少产品层、技术层、模块层、交付层、归档层的边界。
4. **阶段计划冲突**：旧 MVP、支付生产化、论文工作台升级、市场上线风险审计、下一阶段开发计划同时存在，部分内容已是执行记录，部分仍是规划。
5. **有效性难判断**：部分文档写明“已实现 Issue”，部分仍是“建议/规划/待确认”，但根目录没有 README 或状态索引说明哪些是当前基线。

## 3. 是否已从产品决策文档变成开发过程堆积文档

是。当前文档已经混入大量开发过程产物：Issue 拆分、支付修复验收项、实现记录、部署变量、专项审计、订单重构探索等。这些内容仍有参考价值，但不应与产品定位、MVP 流程、用户角色等决策文档同级摆放。

## 4. 当前文档反映出的产品方向

当前产品方向主要是：围绕论文辅导/写作辅助场景，构建学生端、机构端、管理端三方协作的论文任务生产与交付平台。核心链路包括登录、下单、支付、订单任务绑定、阶段生成、论文工作台、Word/DOCX 导出、在线精修、最终交付、后台运营与机构协同。

从文档强度看，近期重点已明显转向：

- 支付模块生产化与风控闭环；
- 论文文档工作台、格式模板、DOCX/OnlyOffice；
- 学术基础数据与 Skill 中心；
- 机构代下单/推单和后台任务分流。

## 5. 当前项目可能存在的产品失焦点

1. **MVP 与平台化能力边界不清**：学术数据、Skill 中心、格式模板、OnlyOffice、支付生产化均很重要，但容易超过市场 MVP 所需。
2. **学生购买转化链路被弱化**：文档中对工作台和后台能力展开较多，而营销页、商品页、首单体验、支付后引导等市场 MVP 入口描述不足。
3. **机构端与学生端优先级冲突**：To B 机构流程、代下单、结算、权限隔离与 To C 自助下单并行推进，但没有明确首发市场选择。
4. **开发 Issue 反向主导产品结构**：大量文档以 Issue 或专项修复为中心，缺少统一的市场 MVP 验证假设。
5. **合规边界需要上升为产品原则**：多处强调不代写、不伪造引用，但尚未沉淀为统一的产品合规红线与页面文案规范。

## 6. 已经过度展开的方向

- 支付专项：从 `payment.md` 到 `14/15/16/17/18/19` 系列，内容丰富但重复，应收敛为技术配置、生产部署、审计清单三类。
- 论文工作台专项：`03-feature-architecture.md`、`09-acceptance-checklist.md`、`15-thesis-workbench-upgrade-plan.md`、`onlyoffice-deployment.md` 都涉及工作台，应拆分产品流程与模块技术实现。
- 计划/Issue 文档：路线图、开发计划、执行计划、下一阶段计划、Issue 列表过多，应归并为交付目录。
- 学术数据导入/同步：已形成专项模块，应从根目录迁入模块目录，避免与产品蓝图混放。

## 7. 仍然是市场 MVP 核心的内容

- 学生自助下单、支付成功、订单任务绑定；
- 任务阶段可视化与最小论文内容生成；
- 合稿与格式、DOCX 导出、下载交付；
- 管理后台处理订单、任务、退款、状态纠偏；
- 明确合规边界：写作辅助、格式整理、学习支持，不承诺代写、伪造数据、伪造引用；
- 若首发市场包含机构，则机构代下单/推单、所属数据隔离、交付进度查看是 MVP 核心；否则应降为 P1。

## 8. 关键问题回答

- **当前 docs 里产品主线是否清晰？** 不够清晰。主线可被推断为“论文任务生产与交付平台”，但被支付、OnlyOffice、学术数据、Issue 拆分等过程文档冲散。
- **是否存在编号重复、主题重复、阶段计划冲突？** 存在，且已影响文档可维护性。
- **是否混合不同层级内容？** 是。产品设计、开发计划、支付专项、OnlyOffice、机构端、学术数据、订单重构均在根目录并列。
- **是否能支撑继续开发？** 能支撑局部继续开发，但需要先明确当前有效基线，否则容易按过期计划继续扩张。
- **是否能支撑对外发行 MVP？** 暂不能直接支撑。还需要收口市场 MVP 流程、页面入口、合规文案、发布验收与风险清单。
- **下一步文档体系应该如何收口？** 先保留旧文档不动，建立 `01-product`、`02-technical`、`03-modules`、`04-delivery`、`90-archive` 分层，再将根目录旧文档按合并映射逐步迁移或归档。
